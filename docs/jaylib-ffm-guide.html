jaylib​-ffm, for the AlgorithmVisualiser project

jaylib-ffm is a Java binding for raylib, the small C library for windows, 2D/3D drawing, input and audio. Instead of JNI, it uses Java's Foreign Function & Memory API (Project Panama) to call straight into the native raylib shared library — no C glue code, no JNI headers. Every function in raylib's C API shows up as a static method on com.raylib.Raylib, and every C struct (Vector2, Color, Texture…) shows up as a small Java class backed directly by native memory.

Two things fall out of that version number: 5.5 is the raylib release being wrapped, and the FFM API it's built on was finalized in JDK 22 — your pom.xml already targets Java 25, so no preview flags are needed. On older JDKs (22/23) you'd need --enable-preview. FFM also requires opting in to native calls:

Native access

If you run the packaged jar directly on JDK 22–23 you may need --enable-native-access=ALL-UNNAMED on the java command line, since FFM native calls are a restricted, opt-in operation. Later JDKs relax or warn instead of failing outright — check your console output for an "illegal native access" warning if something seems oddly silent.

The jar ships prebuilt native raylib binaries for Windows/Linux/macOS inside itself — there is nothing else to install to get a window on screen.

Core Concepts

the four ideas that explain almost every method signature in this library

1. Everything is a static call on Raylib

raylib's C functions map 1:1 to static methods, renamed from PascalCase to camelCase: C's InitWindow(w,h,title) becomes Raylib.initWindow(w,h,title). Struct field names stay as-is. Most files static import com.raylib.Raylib.*; so the whole API reads unqualified, exactly like raylib's own C examples:

import static com.raylib.Raylib.*;

initWindow(800, 600, "Algorithm Visualiser");
while (!windowShouldClose()) {
    beginDrawing();
    clearBackground(RAYWHITE);
    drawText("hello", 190, 200, 20, DARKGRAY);
    endDrawing();
}
closeWindow();

2. Structs are wrapper objects over native memory, with a uniform accessor pattern

Every raylib struct (Vector2, Color, Texture, Camera3D…) is generated the same way, so learning one teaches you all 33. Given a field like Color.r, you get four ways to touch it:

bean getterbyte v = color.getR();
bean settercolor.setR((byte)255);
fluent readbyte v = color.r();
fluent write (chainable)color.r((byte)255).g((byte)0);

Every struct also has four constructors — no-args (auto-managed memory), an Arena-taking no-args version, one that wraps an existing MemorySegment, and one that takes all fields at once (with or without an explicit Arena). equals() compares by native memory identity, not by field value — two Color instances with identical RGBA but separate allocations are not .equals(). Compare fields directly, or use Raylib.colorIsEqual(...) where raylib provides one.

3. Memory lives in an Arena — know who's managing it

FFM struct returns need somewhere to live in native memory. Functions that return a struct come in two flavors: a no-arg version that allocates from an implicit auto-managed arena, and an overload taking an explicit Arena as the first parameter for when you want control over lifetime (e.g. reusing one arena for a whole frame instead of allocating every call). The library's own example code puts it plainly:

try (Arena arena = Arena.ofConfined()) {  // optional — falls back to an auto arena if omitted, but owning one can be faster
    var texBunny = loadTexture(arena, "wabbit.png");
    var mouse = getMousePosition(arena);
    // ... game loop ...
}

For a simple app like a single game-loop window, you can ignore Arena entirely and use the no-arg overloads — that's what auto-arena mode is for. Reach for an explicit Arena once you're allocating structs in a hot loop and want to control when native memory is reclaimed.

4. Buffers must be direct and native-order

A handful of functions (audio callbacks, random sequences) take raw IntBuffer/FloatBuffer/ByteBuffer. These must be direct allocations in native byte order — a plain ByteBuffer.allocate(n) will not work against native code. jaylib-ffm ships three helpers that get this right:

IntBuffer buf = Raylib.createIntBuffer(256);   // also: createFloatBuffer, createByteBuffer

Window & game loop skeleton

The shape every raylib program takes: init once, loop until close is requested, clean up once. This mirrors your own Main.java.

import static com.raylib.Raylib.*;

void main() {
    initWindow(800, 600, "Algorithm Visualiser");
    setTargetFPS(60);

    while (!windowShouldClose()) {
        beginDrawing();
        clearBackground(RAYWHITE);
        // draw calls go here
        endDrawing();
    }
    closeWindow();
}

Basic shapes

All shape-drawing calls (54 of them) must happen between beginDrawing() / endDrawing().

drawRectangle(40, 40, 120, 60, SKYBLUE);
drawCircle(300, 150, 40, MAROON);
drawLine(0, 0, 200, 200, DARKGRAY);
drawTriangle(new Vector2(400,40), new Vector2(360,120), new Vector2(440,120), GOLD);

Handy for a visualiser specifically: array/tree cells as drawRectangle + drawRectangleLines, comparisons highlighted by swapping the fill Color per frame.

Loading & drawing a texture

Load once outside the loop, draw every frame, unload once at the end — textures live in GPU memory (VRAM) and are not garbage collected.

Texture tex = loadTexture("assets/sprite.png");

while (!windowShouldClose()) {
    beginDrawing();
    clearBackground(RAYWHITE);
    drawTexture(tex, 100, 100, WHITE);
    endDrawing();
}
unloadTexture(tex);

Text & custom fonts

The default font works with drawText; for custom fonts, size, and spacing, load a Font and use drawTextEx.

Font font = loadFont("assets/roboto.ttf");
// ...
drawTextEx(font, "Algorithm Visualiser", new Vector2(20,20), 32, 1, DARKGRAY);
// scale text with the window instead of a fixed literal size:
int size = (int)(getScreenHeight() * 0.04f);
drawText("Algorithm Visualiser", windowWidth/2 - 100, windowHeight/2 - 20, size, DARKGRAY);
Relevant to your last commit

Your current Main.java draws text with a fixed 30px size regardless of window size — that's the "text is not resizable" issue. Deriving the size from getScreenHeight() (as above) or from getWindowScaleDPI() is the usual fix, since raylib has no auto-scaling text primitive.

Keyboard & mouse input

if (isKeyPressed(KeyboardKey.KEY_SPACE)) { // pressed this frame only
    // e.g. step the algorithm forward one frame
}
if (isMouseButtonDown(MouseButton.MOUSE_BUTTON_LEFT)) {
    Vector2 pos = getMousePosition();
    // e.g. drag a node in a graph visualiser

isKeyDown is level-triggered (true every frame held); isKeyPressed fires once on the frame the key went down — the distinction matters for anything you don't want repeating 60x/second.

2D camera (pan & zoom)

Useful for a large graph/tree that doesn't fit on screen — wrap your world-space drawing in a Camera2D mode instead of hand-computing offsets.

Camera2D cam = new Camera2D();
cam.target(new Vector2(0,0)).offset(new Vector2(400,300)).zoom(1.0f);

beginMode2D(cam);
    // draw world-space content — pan/zoom applies automatically
endMode2D();

Reusing one Arena for a hot loop

If you're calling struct-returning functions (like getMousePosition) every single frame and profiling shows allocation pressure, own the arena instead of relying on the implicit one:

try (Arena arena = Arena.ofConfined()) {
    initWindow(800, 600, "demo");
    while (!windowShouldClose()) {
        Vector2 mouse = getMousePosition(arena); // same arena, reused each frame
        // ...
    }
    closeWindow();
} // arena and everything allocated from it is freed here

For most visualiser-scale workloads this is a micro-optimization — reach for it only after you've actually measured pressure from the no-arg overloads.
